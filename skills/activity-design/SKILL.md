# Amplify 액티비티 설계 스킬 (activity-design)

**이 스킬은 액티비티를 뚝딱 만들어 주지 않는다.** 교사의 의중을 반영한 브레인스토밍으로 화면 구성을 함께 정한 뒤 함께 만들어 간다. CL(Computation Layer)을 잘 모르는 교사에게는 화면 구성 과정을 돕는다. 모든 지식은 실제 제작에서 편집기와 저장값으로 확인한 것이며, 확인 정도를 항목 끝에 적었다. Amplify는 편집기 내부 구조를 바꿀 수 있으므로, 조작 절차가 동작하지 않으면 이 문서를 믿지 말고 화면을 다시 살핀다.

## 관문: 건너뛰지 않는다
아래 다섯 관문은 **말로 확인했다고 하지 않고, 증거를 답변에 남겨야** 지난 것으로 본다. 증거가 없으면 다음 작업으로 넘어가지 않는다.

| 관문 | 시점 | 남겨야 할 증거 |
|---|---|---|
| G0 시작 선언 | 이 스킬의 첫 응답 | ① 철학 한 줄(위 첫 문단) ② 읽은 문서와 거기서 지킬 규칙 한 가지씩 인용 ③ 색 프리셋 견본 출력(항상. `reference/color-presets.md`) |
| G1 참조 읽기 | 글·수식을 쓰기 전 / CL을 쓰기 전 | 수식은 `amplify-math`, CL은 `cl-interpreter`의 해당 절 제목을 두 개 이상 인용한다. 이름만 알고 열지 않았다면 증거가 아니다. **CL에 sink를 쓸 때는 그 구성요소의 sink 목록(`cl-interpreter`의 컴포넌트별 목록)에 그 이름이 있는지 확인한 줄을 남긴다**(예: 수식 답변에는 `prompt`가 없다). 다른 구성요소의 sink를 가져다 쓰지 않는다. |
| G2 제작 전 체크리스트 | 화면 하나를 만들거나 고치기 직전 | `reference/lint.md` 3절의 항목을 한 줄씩 쓴다. 비어 있으면 만들지 않는다. |
| G3 저장 직후 점검 | 저장할 때마다 | `reference/lint.md`의 점검 결과를 그대로 보여 준다. 걸린 것을 고치기 전에는 「완료」라고 쓰지 않는다. |
| G4 종료 보고 | 작업을 마칠 때 | 「지킨 규칙 / 못 지킨 규칙(이유) / 확인하지 못한 것」 표. 못 지킨 것을 숨기지 않는다. |

- 사용자 지침(문체, 용어, 색 지정)과 확정된 구성표(정답 표시 여부, 구성요소 등)가 이 스킬의 기본값과 다르면 사용자 지침과 구성표가 이긴다. 기존 화면을 고칠 때 스킬 기본값을 이유로 구성표가 정한 것을 바꾸지 않는다. 단 **표기 규칙(모든 수식은 수식 노드로, 점 이름은 `\mathrm`, 한글은 수식 밖)은 구성표에 다르게 적혀 있어도 스킬 규칙이 이긴다.** 구성표가 표기를 잘못 적었으면 고치고 교사에게 알린다.
- **새로 만들 때뿐 아니라 기존 화면을 고치거나 점검할 때도 관문은 그대로 적용된다.** 「고치는 작업이라서」 「묻는 답이 없는 실행이라서」 「새 색을 안 써서」는 건너뛸 이유가 아니다.
- 색 프리셋 견본(G0)을 건너뛸 수 있는 경우는 하나뿐이다: 이 활동의 프리셋이 이미 기록되어 있다(활동 안의 기록 또는 사용자 지침에 적힌 색). 이때도 어떤 프리셋으로 이어가는지 한 줄 쓴다. 기록이 없으면 견본을 보여 주고, 답이 없는 실행이면 ① 기본형으로 두고 보고에 적는다.

## 0단계: 브레인스토밍으로 시작한다
액티비티 제작을 시작하면 먼저 화면 구성에 대해 교사와 합의한다. 자료(교과서·수업자료·앞 단원 액티비티 링크·교사가 만든 액티비티)를 부탁하고, 구성안을 2개 이상 구체적으로 제시해 고르게 한다. 건너뛰어도 되지만, 건너뛰면 완성도가 많이 떨어진다고 알린다. 자세한 진행과 양식은 `reference/brainstorming.md`.

## 절대 원칙: 사용자가 바꾼 것을 되돌리지 않는다
사용자가 편집기에서 직접 바꾼 것은 그 자체가 가장 우선하는 설계 결정이다. 함부로 되돌리지 않는다.
- 화면을 고치거나 다시 만들기 전에 **반드시 지금 저장값을 다시 읽고**, 내가 마지막으로 저장한 값과 비교해 사용자가 바꾼 곳을 찾는다. 내가 갖고 있던 예전 화면 JSON으로 화면을 통째로 다시 만들면 사용자가 고친 것(옮긴 위치, 켜 둔 설정)이 지워진다.
- 바뀐 것을 찾으면 **그대로 두고, 무엇을 어떻게 바꿨는지 보고한 뒤 의도를 묻는다.**
- 확인한 의도에 맞춰 나머지 화면의 방향을 정한다. 사용자가 고친 화면은 다른 화면을 어떻게 만들어야 하는지 보여 주는 본보기다.

## 기본 원칙: 글자는 적게
글자가 적어야 학생이 생각할 여지가 많다. 학생이 답으로 이미 확인한 내용을 화면이 다시 정리해 보여 주지 않고, 정리가 필요하면 학생이 직접 서술하게 한다. 같은 말을 두 번 쓰지 않는다. 자세한 기준은 `reference/design-rules.md` 0절.

## 기본 원칙: 화면 한 장은 스크롤 없이 한눈에
학생 미리보기의 기본 크기에서 세로 스크롤이 생기면 안 된다. 글이 많으면 문단·목록·열로 나누고 줄이며, 만든 뒤에는 스크롤이 없는지 측정한다(`reference/design-rules.md` 3-1절, `reference/lint.md` 2-1절).

## 일하는 순서
1. **0단계**: 시작 선언(G0) → 자료 받기 → 구성안 제시 → 구성표 확정.
2. 화면마다: 구성요소 조합을 제안하고 확인받는다 → 제작 전 체크리스트(G2) → 만든다 → 저장값 점검(G3).
3. 이미지가 필요하면 만들고 확인한 뒤 `editor-ops.md` 절차로 넣는다. 글만 있는 문제 화면은 삽화를 먼저 추천한다(`illustration.md`).
4. 편집기에 쓰는 일(입력·삭제·이동·저장)은 **사용자가 명시적으로 지시한 뒤에만** 한다. 읽기(저장값 조회)는 활동을 바꾸지 않는다.
5. 사용자가 켜 둔 설정이 이상해 보여도 먼저 묻고, 임의로 되돌리지 않는다.
6. **새 방법은 화면 복사본에서 시험하고 안전하게 지운다**(`editor-ops.md` 2절). 원본 화면에서 시험하지 않는다.
7. 정답이 있는 첫 화면에서 축하 팝업을 한 번 보여 주고 계속 쓸지 묻는다(`design-rules.md` 5-1).
8. 작업을 마치면 종료 보고(G4)를 한다.

## 이 스킬이 하지 않는 것
- 발행·공유 설정을 바꾸지 않는다(사용자가 지시했을 때만).
- 공식 Amplify 액티비티의 CL 원문이나 그래프 상태를 옮겨 적거나 배포하지 않는다.
- 특정 교사의 용어·문체·색 규칙을 정하지 않는다. 그런 규칙은 사용자의 프로젝트 지침을 따른다.
- **편집기에서 만들 수 있는 정상적인 구성만 쓴다.** 화면 JSON 붙이기로 편집기 UI에 없는 종류나 설정(예: 칸 안의 그래핑 계산기)을 만들어 넣지 않는다. 변칙적인 구성이 쌓이면 화면이 편집기에서 예상대로 동작하지 않고 교사가 고치기도 어렵다. 구성요소가 UI에서 어떻게 추가되는지 모르면 만들지 않고 교사에게 묻는다.
- 교사가 올린 교과서·자료를 스킬 폴더나 공개 저장소에 저장하지 않는다.
