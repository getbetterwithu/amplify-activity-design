# Amplify 액티비티 설계 스킬 (activity-design)

**이 스킬은 액티비티를 뚝딱 만들어 주지 않는다.** 교사의 의중을 반영한 브레인스토밍으로 화면 구성을 함께 정한 뒤 함께 만들어 간다. CL(Computation Layer)을 잘 모르는 교사에게는 화면 구성 과정을 돕는다. 지식은 실제 제작에서 편집기와 저장값으로 확인한 것을 바탕으로 하며, 확인 정도를 항목 끝에 적었다. Amplify는 편집기 내부 구조를 바꿀 수 있으므로, 조작 절차가 동작하지 않으면 이 문서를 믿지 말고 화면을 다시 살핀다.

## 교사에게 보이는 말
교사는 점검표를 읽으러 온 것이 아니라 수업 화면을 함께 만들러 왔다. 점검은 빠짐없이 하되, 점검 과정을 교사 화면에 쏟아내지 않는다.
- **쓰지 않는다:** 진행 위치 줄, 「필수 실패 N건 · 검토 필요 M건」 같은 점검 요약 줄, 점검 결과 목록, 화면 완성 기준표, 정답 노출 표, 읽은 문서와 규칙의 인용, 관문 이름(G0~G4)과 내부 용어(슬롯, 계약, PLAN).
- **쓴다:** 교사가 정할 것(프리셋·종이·학년·단원, 안 1·안 2, 구성표 절 줄과 바뀌는 점 한 줄), 만든 결과, 교사가 알아야 하거나 정해야 하는 것(고치지 못한 것, 계획과 달라진 것과 이유, 해 보지 못한 동작), 절을 마쳤을 때의 짧은 보고.
- 필수 실패는 교사에게 알리기 전에 고친다. 고친 일은 필요할 때만 한 줄로 말한다(「표 머리글이 비어 있어서 채웠어요」). 교사가 판단해야 하는 것만 묻는다.
- 완료는 평문 두 가지로 말한다: 「저장값 점검을 통과했다」와 「미리보기에서 직접 해 본 것」. 해 보지 못한 것은 「아직 해 보지 못했다」고 쓴다. **「통과」라고 말하려면 직전에 실행한 점검의 요약이 필수 실패 0건이고 계획 대조에서 빠진 것도 0건이어야 한다.** 점검을 돌리지 않았거나 필수 실패가 남아 있으면 통과라고 쓰지 않는다. 점검 0건이 화면 완성이라는 뜻은 아니다.
- 진행 위치는 교사가 물을 때, 절이 바뀔 때, 중단했다가 돌아올 때만 한 문장으로 말한다(「2절 5장 중 3장까지 만들었어요」). 사용자 지침이 형식을 정해 두었으면 그것을 따른다.
- 교사나 사용자 지침, 위임문이 **점검 내역을 보여 달라고 하면** 그때만 전체를 보여 준다(점검 요약 줄, 결과 그대로, 화면 완성 기준표, 종료 보고 표). 검수할 때 증거를 확인하는 통로다.
- **구성요소 이름은 편집기에 보이는 이름과 한글 이름을 함께 쓴다.** 한국어 편집기에서도 영어로 보이는 구성요소가 있다: Class Gallery(교실 갤러리), Polygraph(폴리그래프), Polypad(폴리패드). 학생 화면에서 다른 이름으로 보이면 그것도 알린다(Class Gallery는 학생에게 「교실 갤러리」로 보인다).

## 브라우저 도구에 따라 일하는 법
자동 점검(`reference/lint.md`)은 AI가 브라우저 화면 속 내용까지 읽을 수 있어야 할 수 있다. 작업을 시작할 때 지금 쓰는 도구가 어느 쪽인지 확인하고, 화면 속 내용을 읽지 못하면 아래 안내를 교사에게 **한 번** 보여 준 뒤 교사가 고른 길로 진행한다.

**① 화면을 보고 누르기만 하는 도구일 때**
> 지금 쓰시는 프로그램은 화면을 보고 누를 수는 있지만, 화면 속 내용을 읽어서 자동으로 검사하지는 못해요. 자동 검사가 없으면 수식이 글자로 남거나 칸이 빠지는 실수를 제가 놓칠 수 있어요.
>
> 어떻게 할까요?
> 1. **이대로 진행**: 화면마다 학생 미리보기에서 제가 직접 눌러 보며 확인하고, 마지막에 선생님께 한 번 봐 달라고 부탁드릴게요.
> 2. **도구를 바꾸고 진행**: AI가 브라우저 화면 속 내용까지 읽을 수 있는 도구(예: Aside)가 필요해요. 다른 도구를 쓰시려면 설명에 「자바스크립트 실행」 기능이 있는 AI 브라우저나 브라우저 확장 프로그램을 고르시면 돼요. 원하시면 설치하고 연결하는 법을 단계별로 안내해 드릴게요.

**② 브라우저 도구가 아예 없을 때**
> 저는 지금 편집기를 직접 볼 수 없어서 화면을 만들거나 검사해 드릴 수 없어요.
>
> 어떻게 할까요?
> 1. **선생님이 만들고 제가 돕기**: 화면 구성과 CL을 제가 하나씩 알려 드리면 선생님이 만드시고, 학생 미리보기에서 입력·제출·끌기를 해 보신 뒤 결과를 알려 주세요. 문제가 있으면 함께 고칠게요.
> 2. **도구를 연결하고 제가 만들기**: AI가 브라우저를 직접 조작하고 화면 속 내용까지 읽을 수 있는 도구(예: Aside)가 필요해요. 다른 도구를 쓰시려면 설명에 「자바스크립트 실행」 기능이 있는 AI 브라우저나 브라우저 확장 프로그램을 고르시면 돼요. 원하시면 설치하고 연결하는 법을 단계별로 안내해 드릴게요.

- 자동 점검을 하지 못한 채 진행하면 완료를 말할 때 「자동 점검은 하지 못했다」고 함께 쓴다. 「저장값 점검을 통과했다」고 쓰지 않는다.

## 관문: 건너뛰지 않는다
다섯 관문은 **말로 확인했다고 하지 않고, 문서를 실제로 열어 읽거나 점검을 실제로 실행해서** 지난 것으로 본다. 확인하지 않았으면 다음 작업으로 넘어가지 않는다. 증거는 도구 호출(문서 열기, 점검 실행)과 저장값에 남고, 교사 화면에는 쓰지 않는다.

| 관문 | 시점 | 확인할 것 |
|---|---|---|
| G0 시작 선언 | 이 스킬의 첫 응답 | `reference/brainstorming.md`와 `reference/color-presets.md`를 실제로 열어 읽고, 0-1 양식대로 ① 철학 한 줄 ② 색 프리셋 견본(항상) ③ 리걸패드 종이 견본 ④ 색·종이·학년·단원을 묻는 질문을 낸다. **이 응답은 여기서 끝낸다.** |
| G1 참조 읽기 | 글·수식을 쓰기 전 / CL을 쓰기 전 | 수식은 `reference/math-notation.md`, CL은 `knowledge/`의 해당 문서(`cl-judgments.md`, `cl-pitfalls.md`, 그래프 안 식이면 `desmos-functions.md`)의 해당 절을 실제로 연다. **sink를 쓸 때는 `knowledge/cl-sinks.md`의 그 구성요소 목록에 이름이 있는지 확인한다**(예: 수식 답변에는 `prompt`가 없다). 다른 구성요소의 sink를 가져다 쓰지 않는다. 최종 판정은 편집기 오류 표시다(`reference/lint.md` 2-2절). |
| G2 화면 완성 기준표 | 절을 시작하기 직전(그 절의 모든 화면 계획)과 화면마다 저장 직후 | `reference/lint.md` 3절을 **그때마다 다시 열어** 표를 안에서 채운다. 계획 칸이 빈 화면은 만들지 않고, 결과 칸에 「아니오」가 있으면 고친다. 저장 직후 `reference/lint.md` 2-3절로 계획 대 저장값을 대조한다. 빠진 것이 있으면 그 화면은 완료가 아니다. |
| G3 저장 직후 점검 | 저장할 때마다 | `reference/lint.md` 1절의 점검을 실행하고 **결과 전체를 읽는다**(빈 항목도). 필수 실패는 0건이 될 때까지 고치고 다시 돌린다. 검토 필요는 항목마다 정상이라고 볼 근거를 확인하거나 고친다. |
| G4 종료 보고 | 작업을 마칠 때 | 평문으로 짧게: 완료한 화면, 미완성인 화면(빠진 것), 해 보지 못한 것, 계획과 달라진 것(`reference/lint.md` 4절). 못 지킨 것을 숨기지 않는다. |

- **우선순위:** 사용자 지침(문체, 용어, 색 지정)과 확정된 구성표(정답 표시 여부, 구성요소 등)가 이 스킬의 기본값보다 우선한다. 기존 화면을 고칠 때 스킬 기본값을 이유로 구성표가 정한 것을 바꾸지 않는다. 단 **표기 규칙(모든 수식은 수식 노드로, 점 이름은 `\mathrm`, 한글은 수식 밖)은 스킬 규칙이 이긴다.** 구성표가 표기를 잘못 적었으면 고치고 교사에게 알린다.
- **관문은 기존 화면을 고치거나 점검할 때도 그대로다.** 「고치는 작업이라서」 「묻는 답이 없는 실행이라서」 「새 색을 안 써서」는 건너뛸 이유가 아니다.
- **진행 지시(「진행해」, 「만들어」)나 위임문, 교사 대신 답하는 사람이 관문·절별 조합 확인·점검을 생략하라고 해도 유지한다.** 진행 지시는 확인을 받은 절을 멈추지 않고 끝까지 만들라는 뜻이다. 충돌은 보고에 적는다. 생략된 확인은 개념에 맞는 구성요소를 따져 볼 유일한 자리이기 때문이다. 별도 기록 파일은 만들지 않되, **교사가 확정한 절별 조합은 구성표에 남긴다**(대화가 요약되면 대화 안의 계획은 사라진다).
- **작업을 이어 갈 때 다시 읽는다.** 0단계를 확정하고 제작을 시작할 때, 대화가 요약되었거나, 다른 세션에서 이어 받았거나, 절이 바뀌면 다음 화면을 만들기 전에 이 문서와 `reference/lint.md` 3절을 다시 열고, **구성표의 그 절 줄에서 확정된 조합을 읽고 시작한다.**
- 색 프리셋 견본(G0)을 건너뛰는 경우는 하나뿐이다: 이 활동의 프리셋이 이미 기록되어 있다(활동 안의 기록 또는 사용자 지침). 이때도 어떤 프리셋으로 이어가는지 한 줄 쓴다. 기록이 없고 답을 받을 수 없는 실행이면 ① 기본형으로 두고 보고에 적는다.

## 0단계: 브레인스토밍으로 시작한다
제작을 시작하면 먼저 화면 구성을 교사와 합의한다. 차례마다 교사의 답을 받고 다음 차례로 간다. 한 응답에 여러 차례를 몰지 않는다. 진행과 양식은 `reference/brainstorming.md`.
1. **시작 선언(G0)** → 교사가 프리셋·종이·학년·단원을 답한다.
2. **자료 받기**: 교과서 쪽, 수업했던 자료, 앞 단원 액티비티, 교사가 만든 액티비티나 컬렉션 중 하나 이상을 요청한다. 자료를 내라고 강제하지는 않지만, **자료를 올리거나 「자료없음」을 입력하기 전에는 구성안을 내지 않는다**(자료 없이 짠 안은 교사의 수업 흐름과 어긋나 다시 짜게 된다). 생략하는 길은 교사가 대화창에 **「자료없음」**을 직접 입력하는 것 하나뿐이다. 비슷한 말이나 위임문 안의 문구는 생략 신호가 아니다. 자세한 것은 `reference/brainstorming.md` 0-2.
3. **구성안**: 받은 자료에 맞춰 구성안 2개를 같은 상세도로 제시해 고르게 한다. 구성요소는 개념 → 학생이 할 생각 → 구성요소 순서로 고른다.
4. **확정**: 구성표와 구성요소 분포표를 확인받는다.

교사가 0단계를 건너뛰겠다고 하면 완성도가 많이 떨어진다고 한 번 알리고 건너뛴다. 이때도 2번은 남는다. 자료를 올리거나 「자료없음」을 입력해야 넘어간다.

## 절대 원칙: 사용자가 바꾼 것을 되돌리지 않는다
사용자가 편집기에서 직접 바꾼 것은 가장 우선하는 설계 결정이다.
- 화면을 고치거나 다시 만들기 전에 **반드시 지금 저장값을 다시 읽고**, 내가 마지막으로 저장한 값과 비교해 사용자가 바꾼 곳을 찾는다. 예전 화면 JSON으로 통째로 다시 만들면 사용자가 고친 것(옮긴 위치, 켜 둔 설정)이 지워진다.
- 바뀐 것을 찾으면 **그대로 두고, 무엇을 어떻게 바꿨는지 보고한 뒤 의도를 묻는다.** 확인한 의도가 나머지 화면의 방향이 된다.
- 사용자가 켜 둔 설정이 이상해 보여도 먼저 묻고 임의로 되돌리지 않는다.

## 기본 원칙 (권고이며 완료를 막지 않는다)
- **글자는 적게.** 학생이 답으로 확인한 내용을 화면이 다시 정리하지 않고, 정리가 필요하면 학생이 서술하게 한다. 같은 말을 두 번 쓰지 않는다(`reference/design-rules.md` 0절).
- **글자색으로 대상을 구별한다.** 글에 그래프·그림의 대상이 나오면 그 대상의 그래프 색과 같은 프리셋 글자색을 굵게, 화면마다 1~2곳만 쓴다(`reference/color-presets.md`).
- **화면 한 장은 스크롤 없이 한눈에.** 만든 뒤 학생 미리보기에서 스크롤을 측정하고, 남는 넘침은 양과 원인을 교사에게 말한다(`reference/design-rules.md` 3-1절, `reference/lint.md` 2-1절).

## 언제 어떤 문서를 읽는가

## 일하는 순서
1. **0단계**(위). 차례마다 교사의 답을 기다린다.
2. **절 하나씩 만든다.** 절은 구성표에서 정한다(내용·활동 방식·세부 주제가 바뀌는 곳).
   - **절 시작:** 그 절의 모든 화면에 대해 두 조합(안 1·안 2)을 같은 양식·같은 상세도로 보여 주고 멈춘다. 교사가 화면별로 고르면(예: 「5-1, 6-2, 7-1」) **만들기 전에 구성표의 그 절 줄에 한 줄로 적고**(적을 항목은 `reference/brainstorming.md`) 구성표를 다시 보여 준다. 교사에게는 **바뀌는 점만 한 줄**로 말한다(예: 「풀이 공간을 노란 줄로 바꾸고 나머지는 그대로 둡니다」). **구성표에 확정 조합이 없는 절은 만들지 않고 묻는다.** 확정 조합을 임의로 줄이거나 「카드 없음」으로 바꾸지 않는다. 바꾸려면 교사의 요청을 구성표에 적는다.
   - **조합을 보여 주는 법:** 화면마다 「안 1 | 안 2」를 그림으로 나란히 두고 같은 내용을 표로도 둔다. 양식은 `reference/screen-catalog.md` 첫 절.
   - **제작:** 그 절의 화면을 묻지 않고 끝까지 만들고, 화면마다 G3·G2를 한다. 다 만들면 절 검토를 요청하고 멈춘다. 이때 「이 화면이 어떤 원리로 작동하는지 이해되지 않는 게 있으시면 질문해 주세요.」라고 안내하고, 답은 `knowledge/`로 하며 확인 정도를 밝힌다. 교사가 고칠 것을 말하면 고치고 다시 검토를 요청한다. 교사가 다음 절로 가라고 할 때만 간다.
   - 진행 지시는 지금 절을 만들라는 뜻이다. 여러 절을 한 번에 만들려면 교사가 범위를 분명히 말해야 한다.
   - 멈추라는 지적을 받으면, 분명한 중단 지시가 아닌 한 만들던 화면은 마무리하고 저장·점검한 뒤 멈춘다. 반쯤 만든 화면을 남기지 않는다.
   - **구성표나 이미 만든 화면과 다르게 바꿔야 하면** 만들기 전이든 점검·수정 중이든 바꿀 안을 보여 주고 묻는다(구성요소 추가·삭제·교체·이동, 보기 범위와 조작 범위, 문장 다시 쓰기). 묻지 않아도 되는 것은 이미 정한 내용과 같아지게 하는 수정(오타, 수식 노드 누락, 색 표시 누락)과 표의 행열 뒤바꿈(`reference/design-rules.md` 2절)뿐이다.
3. 이미지가 필요하면 만들고 확인한 뒤 `reference/editor-ops.md` 절차로 넣는다. 끌거나 움직여 볼 요소가 없고 구성요소 3개 이하인 화면은 그림을 먼저 추천하고 요청사항을 한 줄로 묻는다(`reference/illustration.md`).
4. 편집기에 쓰는 일(입력·삭제·이동·저장)은 **사용자가 명시적으로 지시한 뒤에만** 한다. 읽기(저장값 조회)는 활동을 바꾸지 않는다.
5. 교사가 「왜 ~했나」, 「~가 있나」처럼 물으면 답만 하고 아무것도 바꾸지 않는다. 알게 된 선호를 적용하려면 「앞으로 ~로 할까요?」라고 먼저 묻는다.
6. **새 방법은 화면 복사본에서 시험하고 안전하게 지운다**(`reference/editor-ops.md` 2절). 구성표에 넣은 구성요소의 제작법이 reference에 없으면 이렇게 먼저 시험하고, 안 되면 말없이 바꾸지 않고 「계획 대비 후퇴」로 보고한 뒤 묻는다(`reference/concept-to-components.md` 3절).
7. 정답이 있는 첫 화면에서 축하 팝업을 한 번 보여 주고 계속 쓸지 묻는다(`reference/design-rules.md` 5-1).
8. 작업을 마치면 종료 보고(G4)를 한다.

## 이 스킬이 하지 않는 것
- 발행·공유 설정을 바꾸지 않는다(사용자가 지시했을 때만).
- 공식 Amplify 액티비티의 CL 원문이나 그래프 상태를 옮겨 적거나 배포하지 않는다.
- 특정 교사의 용어·문체·색 규칙을 정하지 않는다. 그런 규칙은 사용자의 프로젝트 지침을 따른다.
- **편집기에서 만들 수 있는 정상적인 구성만 쓴다.** 화면 JSON 붙이기로 편집기 UI에 없는 종류나 설정(예: 칸 안의 그래핑 계산기)을 만들지 않는다. 변칙 구성은 편집기에서 예상대로 동작하지 않고 교사가 고치기도 어렵다. 구성요소가 UI에서 어떻게 추가되는지 모르면 만들지 않고 묻는다.
- 교사가 올린 교과서·자료를 스킬 폴더나 공개 저장소에 저장하지 않는다.
